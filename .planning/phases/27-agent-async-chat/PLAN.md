# Фаза 27 — Асинхронный чат агента (мост «ответ агента → чат CRM»)

Дата: 2026-09-17
Статус: implemented

## Проблема

Чат агента был строго синхронным: `POST /agent/send` блокирующе ждал ответ шлюза
Hermes (бюджет 2×300с с ретраем), браузер обрывал fetch через 315с. Internet-запросы
агент легитимно выполняет 5–40 минут (веб-поиск, инструменты) → ответ агента
фактически никогда не возвращался в чат: браузер уже ушёл, обработчик прибивался
вместе с соединением (в `agent_messages` не попадало даже сообщение-таймаут), а
готовый ответ оставался только в сессии шлюза. Приёмной стороны в CRM не было:
единственный писатель `agent_messages` — сам `/agent/send`.

Ретрай в `hermes_service` дополнительно порождал два полных прогона агента на
каждый зависший запрос.

## os_impact

**os_impact: none** — чат агента и его API (`/agent/*`) — внутренний контур CRM
(server-rendered web UI объявлен внутренним, не контрактом, в
`.rai-os/module.yaml` → contracts.provides). Потребление Hermes не меняет контракт
(тот же `:8080 /v1/chat/completions`, фактический интерфейс) — меняется только
поведение клиента (одна попытка вместо ретрая, бюджет ожидания в env). Схема БД,
чужие модули, Party/tenancy/authz, MCP-инструменты не затронуты. Открытые
changes/waivers (.rai-os/changes 001–007, waivers 001–002) не применимы.

## Решение

Асинхронная схема на стороне CRM (RAI_EP не затрагивается):

1. `POST /agent/send` сохраняет сообщение пользователя, запускает фоновую задачу
   (`asyncio.create_task`, живые ссылки в module-level set) и отвечает сразу —
   HTML частичный шаблон сохранённого сообщения пользователя.
2. Фоновая задача вызывает `send_to_hermes` (одна попытка, read-таймаут
   `HERMES_TIMEOUT`, по умолчанию/в env 2400с) и дописывает ответ (или честную
   ошибку) в `agent_messages` собственной сессией БД — независимо от браузера.
3. Новое `GET /agent/updates?after_id=N` — поллинг новых сообщений пользователя
   (id > N) → partial. Это и есть недостающая «подписка» чата на ответы.
4. `agent_chat.html`: после отправки — поллинг раз в 4с пока есть неотвеченные
   запросы; поллинг также стартует при загрузке страницы, если последнее
   сообщение — от пользователя (юзер закрыл и открыл страницу). Клиентский
   AbortController и гонка таймаутов убраны. Если ответа нет дольше
   `HERMES_TIMEOUT + 120с` (сервис перезапускался, фоновая задача потеряна) —
   честная клиентская пометка без записи в БД.
5. `hermes_service.py`: ретрай удалён (одна попытка; повторная генерация того же
   запроса была бессмысленной тратой прогона агента).
6. Разметка сообщения вынесена в `partials/agent_message.html` (один источник:
   страница, ответ send, поллинг). `partials/agent_message_pair.html` удалён.

## must_haves.truths

- POST /agent/send отвечает < 2с при любом агенте (не ждёт прогон).
- Ответ агента появляется в agent_messages и в чате через поллинг, даже если
  браузер закрыт в момент готовности ответа.
- Ошибки агента (таймаут/соединение/HTTP) попадают в чат как сообщение
  ассистента — молчаливых пропаданий нет.
- Ни один клиент чата не использует удалённые `client_timeout`/
  `agent_message_pair.html` (правило зависимостей).
- scripts/test_agent_async.py зелёный локально (TestClient, фейковый агент,
  прод-БД не трогается); scripts/verify.py зелёный.

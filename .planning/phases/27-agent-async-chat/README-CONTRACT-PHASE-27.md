# README-CONTRACT — Фаза 27: асинхронный чат агента (мост «ответ → чат CRM»)

Дата: 2026-09-17
Вердикт: **DONE** (зелёная, деплой — см. «Деплой» ниже)

## Проблема (что было)

Чат агента был синхронным: `POST /agent/send` блокирующе ждал прогон агента
(до 2×300с с ретраем), браузер обрывал fetch через 315с. Internet-запросы идут
5–40 минут → ответ агента не попадал в чат: соединение рвалось, обработчик
прибивался, в `agent_messages` не было даже сообщения-таймаута (кейс 16.09
10:57 — ответ вообще не записан), готовый ответ оставался только в сессии
шлюза hermes. Приёмного механизма («подписки») в CRM не существовало.

## Что сделано

- `POST /agent/send` теперь мгновенно сохраняет сообщение пользователя и
  отвечает его partial'ом; прогон агента — фоновая `asyncio`-задача с живыми
  ссылками (module-level set), пишет ответ/ошибку в `agent_messages` собственной
  сессией (`app/routes/agent.py`).
- Новый `GET /agent/updates?after_id=N` — поллинг новых сообщений (id > N),
  partial. Это недостающая «подписка» чата на ответы агента.
- `agent_chat.html`: поллинг раз в 4с, пока есть неотвеченные запросы; при
  загрузке страницы поллинг продолжается, если последнее сообщение —
  пользовательское (сервер отдаёт возраст `pending_age`). Убраны
  AbortController и гонка клиент/сервер-таймаутов. Если ответа нет дольше
  `HERMES_TIMEOUT+120с` — клиентская пометка «запрос потерян (перезапуск?)»
  без записи в БД.
- `hermes_service.py`: ретрай удалён (одна попытка — двойной полный прогон
  агента был бессмысленной тратой); тексты ошибок обновлены под асинхронный
  режим.
- `HERMES_TIMEOUT` переосмыслен: бюджет ожидания фонового прогона
  (дефолт/env 2400с). `HERMES_CLIENT_TIMEOUT_BUFFER` удалён за ненадобностью.
- Разметка сообщения — единый партиал `partials/agent_message.html`
  (`data-msg-id` = курсор поллинга); `agent_message_pair.html` удалён.

## Известные ограничения (не долги, осознанные решения)

1. Перезапуск контейнера теряет незавершённые фоновые прогоны (задача в
   памяти). Клиент через `HERMES_TIMEOUT+120с` покажет «запрос потерян» —
   пользователь повторит запрос. Персистентная очередь задач — за рамками фазы
   (не нужна, пока единственный источник задач — чат).
2. «Очистить историю» во время прогона: ответ всё равно допишется после
   завершения (строка появится в пустом чате). Косметика, отдельной фазы не
   требует.
3. Поллинг 4с вместо push (SSE/WebSocket): осознанно — минимальный дифф,
   HTMX-стиль репо. SSE — возможная будущая оптимизация.

# Фаза 28 — Персистентная очередь прогонов агента (agent_jobs)

Дата: 2026-09-17
Статус: implemented
Закрывает известное ограничение фазы 27 («перезапуск контейнера теряет
незавершённые фоновые прогоны»).

## Проблема

Фаза 27 сделала чат асинхронным, но фоновые прогоны жили только в памяти
процесса: рестарт контейнера (деплой, `docker restart`, OOM) терял запущенные
запросы — пользователь ждал ответ, который уже никто не доставит.

## os_impact

**os_impact: none** — новая таблица `agent_jobs` и эндпоинты `/agent/*` —
внутренний контур CRM (server-rendered web UI — «внутренний, не контракт»,
module.yaml). Чужие модули, внешние API, Party/tenancy/authz не затронуты.
Схема БД расширяется новой таблицей через штатный create_all (без ALTER).
Потребление Hermes — тот же эндпоинт, добавлен опциональный заголовок
`Idempotency-Key`, который шлюз уже поддерживает (дедупликация повторов) —
это использование существующего поведения, не новый контракт.

## Решение

1. Таблица `agent_jobs` (models.py): user_id + снимки user_name/role (прогон
   при восстановлении идёт с исходным контекстом), message, context_lead_id,
   search_mode, статус pending → running → done|failed (+ cancelled при
   «Очистить историю»), agent_message_id, error, created_at/updated_at.
2. `/agent/send` создаёт сообщение пользователя и задачу одним коммитом,
   обработка — `_process_job(job.id)` фоновой задачей (сессии своя на шаг).
3. `recover_stuck_agent_jobs()` из lifespan при старте: pending/running задачи
   перезапускаются; повторный запрос в шлюз идёт с `Idempotency-Key:
   crm-job-<id>` — если оригинал ещё считается/кэширован на шлюзе, ответ
   вернётся без второго полного прогона.
4. Самолечение в `/agent/updates`: прогон, висящий дольше
   HERMES_TIMEOUT+900с, закрывается со статусом failed и честной ошибкой в
   чате (процесс убит без шанса на recovery — например, SIGKILL до старта).
5. «Очистить историю» отменяет незавершённые задачи (status=cancelled) —
   фантомные ответы больше не дописываются в пустой чат.
6. Клиент: `data-jobs-pending` на странице + маркер `agent-jobs-marker` в
   ответе updates — решение «ждать или признать потерю» принимается по
   серверной истине, а не по таймеру (3 опроса подряд без ответа и без
   незавершённых задач → пометка «запрос потерян», поллинг останавливается).
   Во время рестарта сервера поллинг просто пережидает сбои сети.

## Сопутствующая ops-правка (вне репо, зона hermes/RAI_EP)

`web.extract_backend: trafilatura` в /root/.hermes/config.yaml был корректен,
но сервис hermes-team (запущен 11.09) не видел ни установленного пакета
trafilatura, ни плагина → фолбэк на SearXNG («search-only») → каждый extract
падал, internet-прогоны растягивались на десятки минут. Фикс: рестарт
hermes-team (переоткрытие плагинов). Проверено вызовом провайдера напрямую
(registered/available/extract OK); Tavily-ключ из coach-nika — запасной
вариант, не понадобился.

## must_haves.truths

- Отправленный запрос агента переживает рестарт контейнера: после старта
  ответ дописывается в чат без действий пользователя.
- «Очистить историю» во время прогона не даёт фантомного ответа.
- Клиент чата не вешается навечно: потеря прогона видна по серверному
  маркеру и честно показывается.
- scripts/test_agent_jobs.py зелёный (включая симуляцию восстановления через
  реальный lifespan); scripts/test_agent_async.py и scripts/verify.py
  остаются зелёными; прод-БД локально не трогается, тест чистит за собой.

# README-CONTRACT — Фаза 28: персистентная очередь прогонов агента (agent_jobs)

Дата: 2026-09-17
Вердикт: **DONE** (закрывает известное ограничение фазы 27)

## Проблема

Фоновые прогоны агента (фаза 27) жили в памяти процесса: рестарт контейнера
(деплой, restart, OOM) терял запрос — пользователь ждал ответ, который уже
никто не доставил.

## Что сделано (CRM)

- Таблица `agent_jobs`: снимки контекста (user_name/role), статус
  pending → running → done|failed (+ cancelled), agent_message_id, error.
  Создаётся штатным create_all, без ALTER.
- `/agent/send`: сообщение + задача — один коммит; обработка фоновой задачей
  `_process_job()` (сессии на каждый шаг, отмена проверяется перед записью).
- `recover_stuck_agent_jobs()` из lifespan: при старте pending/running
  перезапускаются; повтор идёт с `Idempotency-Key: crm-job-<id>` — шлюз может
  вернуть результат живого оригинала без второго прогона.
- Самолечение в `/agent/updates`: прогон дольше HERMES_TIMEOUT+900с → failed
  + честная ошибка в чате (процесс убит без шанса на recovery).
- «Очистить историю» отменяет незавершённые задачи — фантомные ответы
  исключены.
- Клиент: решение «ждать/потеряно» по серверному маркеру
  (`agent-jobs-marker`, `data-jobs-pending`), не по таймеру; во время
  рестарта поллинг пережидает сетевые сбои.

## Известные ограничения

1. Recovery перезапускает прогон заново; если оригинал на шлюзе ещё работал,
   возможен второй полный прогон (Idempotency-Key снижает вероятность, но не
   гарантирует — поведение кэша шлюза не контрактовано).
2. cancelled-задача не прерывает сетевой запрос к шлюзу — агент может
   доработать «в никуда» (ответ не пишется). Дешевле, чем отменять HTTP.

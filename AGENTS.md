# AGENTS.md — локальные правила агентов для CRM RAI

Проект: CRM RAI (FastAPI + SQLite + HTMX, донор процессов продаж для RAI OS).
Репозиторий управляется по RAI OS Governance Protocol — см. `.rai-os/`.

## Обязательный порядок работы (GSD + RAI OS)

1. **До написания или исполнения любого PLAN** — классификация OS-impact
   (governance §6, обязательна с фазы 24):
   - прочитать `.rai-os/module.yaml` и `.rai-os/policy-lock.yaml`;
   - проверить ОТКРЫТЫЕ записи `.rai-os/changes/`, `.rai-os/waivers/` и применимые
     директивы в `.rai-os/directives/`;
   - классифицировать: затрагивает ли работа общий API/событие/AI-инструмент/схему,
     идентичность, тенантность, авторизацию, Party-идентичность, владение данными,
     межмодульные enum, A-RAI/HITL, общий дизайн/навигацию, топологию деплоя;
   - если ДА — создать `.rai-os/changes/<ID>.yaml` (status: proposed) ДО реализации
     и включить ID директив/требования контрактов в `must_haves.truths` PLAN;
   - если НЕТ — зафиксировать в PLAN одну строку «os_impact: none, причина».
2. Внутренний рефакторинг, локальные тесты, тексты и не затрагивающие контракты
   UI-правки записи изменения не требуют (если не задета системная граница).
3. Фаза не завершена, пока применимая директива P0/P1 не решена или её проверка
   красная (кроме случая, когда область покрыта действующим waiver).

## Границы владения (canon)

- CRM RAI владеет ТОЛЬКО sales-domain состоянием: лид/сделка/КП/активность.
- Каноническая Party-идентичность — `must_not_own` (владелец: rai-ep Party Registry).
- Не записывать в БД других модулей; не создавать конкурирующих реестров организаций.
- Прямые записи MCP (`mcp_server.py`) — фактический внутренний интерфейс,
  НЕ утверждённый контракт OS (CRM-RAI-OS-CHANGE-003 / RAI-OS-WAIVER-001).

## Технологические правила репо

- Сервер: только `/srv/crm-rai/` (ssh `rai-dev`), `/srv/rai/` — чужой проект.
  Подробности: `.planning/SERVER_ACCESS.md`.
- Миграции схемы: сейчас `create_all` + идемпотентные ALTER в `app/database.py`
  при старте (пробел CRM-RAI-OS-CHANGE-004) — новые ALTER добавляются по образцу
  существующих, с сохранением идемпотентности.
- Локальные проверки фазы: `scripts/verify.py` + профильные `scripts/test_*.py`
  (TestClient на локальной копии БД; прод-БД не трогать).
- Валидация манифестов RAI OS: `python scripts/rai_os_validate.py` — обязательна
  после любых правок в `.rai-os/`. CI в репо нет; при появлении — включить
  обязательной проверкой.
- UI — строго по `.planning/canon/VISUAL_CANON.md`.
- Секреты/`.env`/прод-payload/`storage/crm.db` в git не попадают и не копируются
  в артефакты управления (evidence без секретов).
